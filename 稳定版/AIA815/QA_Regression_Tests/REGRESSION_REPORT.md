## 一、三处改动逻辑审查结论：均正确

### 改动 1 · `tryExtractDateTime` 捕获组索引修复（`idx = 2`）
- **原 bug**：读取第 1 捕获组（年份 2026）后未推进 `idx`，`nextInt()` 链又从第 1 组读成「月份」→ `month=2026` 非法 → 整条日期解析失败（返回 nil，即原始的「isoTime=nil」）。
- **现状**：`idx = 2` 已正确设置；`firstStr.count == 4` 时 `y=年份`，后续依次读月/日/时/分/秒，逻辑正确。
- **验证**：样例 A、B 均正确产出 `2026-07-21` + 对应时分秒。

### 改动 2 · `extractMerchant`：标签 3 字守卫 + 金额独占行上方兜底 + 金额同行商户
- **标签 3 字守卫**：`收款方`/`收款方全称` 捕获组要求 `{3,}`。样例 A 中 OCR 错字「收款方金称」→ 捕获「金称」仅 2 字 → 不匹配，成功避免「金称」残字。✓
- **金额独占行上方兜底**：`阿里云` 位于 `-10.00` 正上方 → 命中返回 `阿里云`（样例 A）。✓
- **金额同行商户**：`阿里云   ¥10.00` → `#"^(.+?)\s*[¥￥]\s*\d"#` 捕获左侧 `阿里云`（样例 C）。✓
- **`isValidMerchant` 增加 `count>=2`**：正确，过滤单字噪声。

### 改动 3 · `extractISODateTime`：带标签时间行第 1 优先级 + 两栏兜底
- 第 1 优先级 `labeledPatterns` 直接把「支付时间」与后续（可跨换行，`\s*` 含 `\n`）时间戳匹配。样例 B「支付时间\n2026-07-21 19:09:35」→ 正确提取。✓
- 两栏兜底 `lines[i..<min(i + 5, lines.count)]`：**越界安全**（`i < i+5 ≤ count`，切片下界 < 上界 ≤ count）。✓

## 二、三项重点疑问复核

| 疑问 | 结论 |
|---|---|
| ① 金额同行正则 `#"^(.+?)\s*[¥￥]\s*\d"#` 是否误吞多行？ | **不会误吞多行**：`.` 默认不匹配 `\n`，`(.+?)` 限定在单行内。但 `^` 仅锚定行首（未开 multiline），故该分支**只在「金额+商户」位于文本第 1 行时生效**；多行账单中若该行在第 2+ 行则不触发（遗留风险④-1）。 |
| ② 金额独占行上方兜底会不会把「支付时间」等非商户行当商户？ | **存在遗留风险（已复现）**：当金额独占行正上方是时间标签行（如「支付时间」），因「支付时间」不在 blocklist、且不含 `HH:MM` 不被 `isLikelyTime` 拦截，会被误判为商户；日期串「2026-07-21 19:09:35」若紧贴金额行上方也会整串被当商户。本次必测样例未触发（真实修复场景金额行上方为「阿里云」）。 |
| ③ 两栏兜底 `lines[i..<min(i+5,...)]` 是否越界安全？ | **安全**，无越界。 |

## 五、遗留风险

1. **金额同行商户分支仅匹配第 1 行**：`^` 未开 multiline，若「商户 ¥金额」出现在账单第 2 行及以后，该分支不生效，退化为标签/兜底逻辑。建议去掉 `^` 锚点或改为按行遍历。
2. **`extractAmount` force 模式误吞日期月份**（详见工程师消息）：真实带 `¥` 金额账单不受影响（显式分支 score=100 稳压），但无 `¥` 且日期紧邻支付标签时金额会错（如样例 B 的 `7.0`）。
3. **金额行上方兜底的时间标签/日期串误判**：建议把「支付时间/付款时间/交易时间/创建时间」加入 blocklist，并把 `isLikelyTime` 扩展为同时识别日期串（含 `-` 的 `YYYY-MM-DD HH:MM:SS`）。
4. 上述均未触及本次三处改动的正确性。
