## 横条/圆环动画「急促 + XS Max 无动画」修复（2026-08-13，方案 A+B+C 落地）
- 用户反馈：iPhone 17 Pro 横条/圆环生长动画「急促不够优雅」；XS Max（A12）横条/圆环「没有显示生长动画」。
- **根因**：①`AIATheme.Motion.draw/progress` 是 `easeOut(0.8/0.6)`——「先快后慢」，前 30% 时间跑完 60% 进度 → 视觉急促；②`RingView` 仍保留 `.onChange(of: progress){animateRing()}`——健康数据每次刷新就重启动画（4 个圆环同时急促飞跃），且无 `max`，progress 瞬态回 0 时圆环「先涨后缩再涨」；③`MiniBar.onAppear` 延迟 0.9s 太久，用户视觉以为页面加载完就该看到进度条，XS Max 上错过动画。
- **改动**（三处）：
  1. `AIAKit/AIATheme.swift` `Motion`：`draw/progress` 从 easeOut 改 `interpolatingSpring(stiffness:60/80, damping:15/17)`（spring 前后缓冲：开始稍缓、中段匀速、末段柔和减速，比 ease-out 优雅）。
  2. `UIComponents.swift` `RingView`：删 `.onChange(of: progress)`，只在 onAppear 播一次；`animateRing` 加 `max(drawn, progress)` 只升不降（对齐 MiniBar 哲学）。
  3. `UIComponents.swift` `MiniBar.onAppear`：`Task.sleep` 从 900ms 缩短到 300ms，用户更早看到生长，XS Max 老芯片也能捕捉完整过程。
- 与 `MacroCard` 已加的 `max(drawn, progress)` 只升不降一致。
- `read_lints` 无报错。

## 首页 MiniBar 首播链路重构（2026-08-13 第二轮落地）

### 上一轮的判断（8-12）
- 冷启动 0.9s 在 `performOnAppear` 延迟 `homeEnterToken &+= 1` → MiniBar `.onChange(of: resetToken)` → `replayMini()`（淡出→归零→淡入）。
- 用户拍板：撤掉这段 + 把首播下沉到 `MiniBar.onAppear` 自己延迟 ~0.9s + 「返回首页」也播。

### 本轮落地（三处改动）
1. **`UIComponents.swift` `MiniBar.onAppear`**: `Task.sleep(50_000_000)` → `Task.sleep(900_000_000)`，注释更新为「等入场弹簧跑完，A12/XS Max 也能从容播完」。

3. **`ContentView.onChange(of: router.path)`**: 新增下降沿判断 `!old.isEmpty && new.isEmpty`（从子页退回首页）→ `homeEnterToken &+= 1` → MiniBar `replayMini()` 重播。

### hot path 收敛
首播/重播 token `homeEnterToken &+= 1` 的三条触发：
- 冷启动：交给 `MiniBar.onAppear` 内置 0.9s 自播，根视图不碰。
- 热启动（回前台）：`didBecomeActive`（保留原逻辑）。
- 返回首页（新）：`router.path` 下降沿。

### 清理
- `@State private var homeEnterFired` 整个文件再无引用，删除字段声明。注释 1210-1212 行相应更新为三条触发路径。

### 教训
- 「外层做延迟补播」和「内层 onAppear 自播」撞同一帧窗口时，外层那次会被合并/跳帧，老芯片直接吞掉。让内层自己播更稳。
- `homeEnterToken` 这种「跨子视图重置动画」令牌，集中放在根视图更新，由子视图统一监听，比「多处各自更新令牌」更不易出 race。

## 首页饮食宫格热量进度条「先生长后变空」修复（2026-08-13 落地）

### 现象
冷启动后，饮食记录宫格顶部热量达成进度条（`MiniBar`）先播一段生长动画，随后被缩回空状态。截图：543 kcal 数字正常，进度条空。

### 根因（value 经历「非零→0」回退）
- 进度条 value = `hd.calorieGoal > 0 ? todayCalories / hd.calorieGoal : 0`（`ContentView.swift` 1514 行，DietTileView）。
- `calorieGoal` 走 `tdeeGoalFallback = mifflinBMR(weightKg:heightCm:age:isMale:) ?? 0 * activityMultiplier`。冷启动时云端 profile 未拉到（或用户未填体重/身高）→ `mifflinBMR` 因 `weightKg<=0 || heightCm<=0` 返回 nil → 结果为 **0** → value 被兜底成 0 → 进度条空。
- 时序：T0 本地无身体数据 → calorieGoal=0 → value=0；T1 `coldStartSync()` 从云端写回体重身高到 UserDefaults，但 `HomeHealthData`（ObservableObject class）里 `@AppStorage` **不会自动发 objectWillChange**，calorieGoal 不立刻重算；T2 `HealthManager.debouncedChange`（300ms 去抖）触发 objectWillChange → body 重算 → 此时体重身高已填 → calorieGoal=1907 → value 突变为 0.28 → `.onChange(of: value)` 触发**生长动画**；T3 再次重算时某瞬态 calorieGoal=0 → value 回 0 → **缩短动画**「再变空」。
- `MiniBar.animateMini()` 原实现是无脑 `withAnimation { drawn = value }`，value 从非零回 0 时会把 drawn 从 0.28 动画缩回 0。

### 修复（两处）
1. **`UIComponents.swift` MiniBar.animateMini() 改「只升不降」**：`drawn = max(drawn, value)`。value 即使瞬时回 0，drawn 停在已涨到的位置；下一帧回升后直接保持。`.onChange(of: value)` 不动。**注意**：`replayMini()`（返回首页/热启动重播路径）特意先归零再生长的逻辑**保留**——它是有意重播，不该被"只升不降"影响。
2. **`ContentView.swift` HomeHealthData.tdeeGoalFallback 加保底**：`mifflinBMR` 缺体重身高返回 nil 时，给通用成人 TDEE 估算 `2000`（非 0 分母），避免冷启动空档期 calorieGoal=0；填了身体数据仍按 Mifflin 精确算（保留原 `bmr * activityMultiplier`，且给 multiplier 加了 `>0 ? : 1.375` 防御）。

### 验收要点
- 冷启动首屏：饮食宫格热量进度条应稳定停在正确比例（如 543/1907≈28%），不再出现「长到 28% 又缩回 0」。
- 返回首页/热启动仍保留 `replayMini()` 的淡出→归零→淡入重播（那是预期动画）。
- 真机 XS Max 老芯片重点看是否还有第二次变空。

### 教训
- `@AppStorage` 在 ObservableObject class 里只是 UserDefaults 同步读取包装，**不会自动 objectWillChange**——这是「值被 CloudSync 改了但视图不重算，然后某次 HealthKit 回调重算时读到新旧中间态」这类 bug 的温床。
- 进度条 value 表达式里，分母（calorieGoal）一旦可为 0，必须保证「非 0 分母」，否则进度条会被 `>0 ? : 0` 兜底成 0。

## 进度条生长动画「老机型不丝滑」修复（2026-08-13 方案 A 落地）
- **现象**：上次修完「不缩回空」后，XS Max(A12) 上 `MiniBar`/`MacroCard` 进度条生长动画仍卡顿/掉帧。
- **根因**：进度填充用 `.frame(width: geo.size.width * safeFraction(drawn))`，`drawn` 每帧变化→width 每帧变→触发整棵树布局重排 + RoundedRectangle/Capsule 重新光栅化，老芯片 CPU 扛不住。
- **修复（方案 A，ask 确认后落地）**：`UIComponents.swift` 两处（`MiniBar` 389-393、`MacroCard` 349-353）改为「固定全宽 + mask 裁剪」：
  ```swift
  RoundedRectangle(cornerRadius: height/2).fill(color)
      .frame(width: geo.size.width, height: height)      // 固定全宽，不再每帧改宽
      .mask(alignment: .leading) {
          Rectangle().scale(x: safeFraction(drawn), anchor: .leading)  // scale=transform 纯 GPU
      }
      .opacity(fillOpacity)
  ```
- **原理**：`.mask` 走 GPU 合成层，`scale(x:anchor:)` 是 transform 不触发布局重排，比每帧改 width 流畅得多。生长边是直边（在 track 圆角内壁中间位置，视觉无瑕疵）。
- 动画令牌 `AIATheme.Motion.progress = easeOut(0.6)` 未改（保持 0.6，避免回调观感变化）；`animateMini()` 的「只升不降 max」和 `replayMini()` 重播逻辑保留。
- `read_lints` 无报错。真机 XS Max 验收：冷启动/返回首页/热启动的生长动画应更顺滑。

## MiniBar/MacroCard 动画彻底简化（2026-08-14 落地，对齐 GrowthBars 竖条哲学）

### 现象
- 方案 A（mask+scale）落地后，XS Max 上横条生长动画仍不够丝滑；竖条柱状图 `GrowthBars`（只动画 height + 错峰 0.07s 延迟）则丝滑。用户截图对比三处：①首页饮食/健康宫格 MiniBar ②饮食记录页的横条+柱状 ③近7日柱状图竖条（丝滑参考）。

### 根因（比 mask 更深）
- `MiniBar.value` 由 `HomeHealthData` 驱动，`HealthManager.debouncedChange` 300ms 一跳 → `.onChange(of: value)` 每 300ms 触发一次 `animateMini()` → 每 300ms 启动新的 `withAnimation` 事务反复插值重算进度条（饮食+健康两个并发生长）。叠加 `replayMini` 的 fadeOut→归零→fadeIn 链式动画，老芯片 A12 每帧要算多个 binding，CPU 扛不住。
- 竖条 `GrowthBars` 只用 1 个 `barsRevealed` Bool 触发一次，7 根错峰，动画结束无后续扰动 → 丝滑。二者哲学差异：**反复重启 vs 一次播完**。

### 改动（UIComponents.swift）
1. **`MiniBar`**：
   - 删 `@State fillOpacity`、`replayGen`（fade 链专用，整段无用）。
   - 删 `.onChange(of: value) { animateMini() }`（数据 300ms 一跳不再反复重启动画，进度条安静停末值）。
   - 删 `replayMini()` 函数（fade 链），`.onChange(of: resetToken)` 改为直接 `drawn = 0; animateMini()` 归零重播单段。
   - 保留 `onAppear` 0.9s 延迟自播 + mask+scale（GPU 合成）+ `animateMini` 只升不降（max 防瞬态回 0）。
2. **`MacroCard`**：删 `.onChange(of: progress) { animateMacro() }`，只保留 `onAppear` 播一次；`animateMacro` 同步加 `max(drawn, progress)` 只升不降。

### 行为变化（重要）
- 不传 `resetToken` 的调用点（BillCategoryView/RecordsViews 的预算、热量指标 MiniBar）：删掉 `.onChange(of: value)` 后，进度条只在进入页面时播一次，之后 value 变化不再追着变。这些页面 value 进入时基本固定，影响小，符合"安静停末值"预期。
- 首页饮食/健康传了 `homeEnterToken`：进入/回前台时归零重播单段生长，中间步数等数据刷新不打扰——正是目标效果。

### 验证
- `xcodebuild ... generic/platform=iOS Simulator build CODE_SIGNING_ALLOWED=NO` → **BUILD SUCCEEDED**。
- 真机 XS Max 验收：首页饮食/健康横条进入/回前台应像竖条一样只播一次顺滑生长，数据刷新不再反复抖动。

### 教训
- SwiftUI 进度条动画想丝滑，关键不只是"用 GPU 合成（mask/scale）"，还要**避免数据高频刷新反复重启 `withAnimation` 事务**。进入/回前台播一次即可；实时数据用文本数字展示，进度条停在末值。

## 横条/圆环动画「XS Max 仍无动画 + 17 Pro 圆环急促」终极修复（2026-08-14 落地，mask→trim 路径重算）

### 现象
- XS Max（A12）：横条/圆环**完全看不到生长动画**（上次方案 A mask+scale 仍无效）。
- iPhone 17 Pro：横条 OK（起步稍缓→匀速→柔和收尾），但健康页 4 个圆环生长仍「急促」。

### 根因（两个不同问题叠加）
1. **XS Max 无动画 = mask 内 transform 老芯片不逐帧重绘**：`MiniBar` 用 `.mask(alignment:.leading){ Rectangle().scale(x:drawn, anchor:.leading) }`，scale 是合成层 transform；A12 上 mask 内 transform + `withAnimation` 常被当单帧跳变 → 直接到终点不见生长。对照铁证：`GrowthBars` 用 `.frame(height:)`（布局驱动）在 XS Max 能逐帧动画。
2. **17 Pro 圆环急促 + XS Max 圆环无动画 = spring 被同事务吞掉**：`RingView.onAppear { animateRing() }` 是**同步**调用，`drawn:0→progress` 与首次布局同帧，SwiftUI 把它当初始值 → 动画被吞（17 Pro 表现成"直接跳满显急促"、XS Max 完全看不到）。而 `MiniBar.onAppear` 用了 `Task.sleep(300ms)` 异步延迟脱离同事务 → 17 Pro 横条正常。
3. **圆环急促放大器**：`Motion.draw` 是 `interpolatingSpring(stiffness:60)`，spring 前期冲量在**整段大圆弧**弧长上放大 → 视觉更冲（横条弧长短所以从容）。

### 改动（4 处，全落地 + BUILD SUCCEEDED）
1. **`AIAKit/AIATheme.swift` Motion 加 `ring`**：`public static let ring = Animation.easeOut(duration: 0.9)`（圆环大圆弧，用稍长缓出起步快收尾柔，比 spring 从容）。
2. **`UIComponents.swift` `RingView`**：`onAppear` 从同步改 `DispatchQueue.main.async { animateRing() }` 延后一帧脱离同事务；`animateRing` 用 `AIATheme.Motion.ring`（替代 draw）。
3. **`UIComponents.swift` `MiniBar`**：生长从 mask+scale 改 **`Capsule().trim(from:0,to:safeFraction(drawn)).stroke(color, lineWidth: height, lineCap:.round)`**（path 重算同圆环，老芯片逐帧可靠，不走 width 布局重排不卡顿，stroke 线宽=高度视觉等同实心胶囊）；`.onChange(of:resetToken)` 的同步 animateMini 也包 `DispatchQueue.main.async` 延后一帧。
4. **`UIComponents.swift` `MacroCard`**：同步 trim 化（`Capsule().trim + stroke(lineWidth:4)`），`onAppear` 也加 async 延后一帧。

### 技术要点
- **矩形实心条"从左生长"的可靠写法**：`Capsule().trim(from:0,to:t).stroke(color, style: StrokeStyle(lineWidth: 高, lineCap: .round))`——trim 是 path 重算（老芯片可靠），stroke 线宽=高度出实心胶囊，不依赖 mask transform，不每帧改 width。
- **同步 `onAppear` 触发动画会被 SwiftUI 当初始值吞掉**：凡 `withAnimation` 在 onAppear 里直接调，都要 `DispatchQueue.main.async`（或 Task.sleep）延后一帧脱离首次布局事务，动画才被识别。这是 XS Max 圆环/横条无动画、17 Pro 圆环"跳满显急促"的共同根因之一。
- mask+transform（合成层）在老芯片 A12 不可靠，`.trim` path 重算 / `.frame(height:)` 布局驱动才逐帧可靠。

### 验收要点
- XS Max：冷启动首页饮食/健康横条、健康页圆环应能看到完整生长动画。
- iPhone 17 Pro：健康页 4 圆环生长应明显从容（缓出 0.9s），不再急促。

## 首页圆环(RingView)/营养条(MacroCard) 老芯片不显示动画「首播守卫」修复（2026-08-13 落地）

### 现象
- 上一轮（mask→trim 终极修复）后：iPhone 17 Pro 动画正常，但 XS Max(A12) 圆环仍不显示。

### 根因
- `RingView` 只在 `.onAppear { animateRing() }` 播一次，而首页宫格卡片自身有入场动画（animateTiles 延迟 16ms + 末位 idx*0.04s + ~0.4s 弹簧）。老芯片首屏渲染慢、`progress` 是在 onAppear 之后才异步填进来 → `animateRing()` 读到 progress=0 → `withAnimation { drawn=max(0,0) }` 等于没动，环定格 0。

- 效果：新芯片 onAppear 数据已就绪直接首播（onChange 不触发）；XS Max 数据晚到 → progress 首次 >0 时 onChange 补播一次生长。后续数据刷新（300ms 一跳）不再重播，动画安静停末值。

- **方案 A（用户拍板"按你建议改"）**：让 SwiftUI `WindowGroup` 直接托管界面（单一全屏 window）。
  - `AIAApp.swift`：`body` 改 `WindowGroup { RootView() }`；新增 `RootView`（按 `AppDelegate.sharedContainer`/`containerReady` 通知切占位↔真实）、`MainOrLoginView`（按 `authStateChanged` 通知切首页↔登录页）、`StartupLoadingView`（占位）；`.onOpenURL`→`AppDelegate.handleOpenURL`、`@Environment(\.scenePhase)` onChange→`AppDelegate.handleScenePhase`。
  - `AppDelegate.swift`：删 `UIWindowSceneDelegate` 协议 + `scene(_:willConnectTo:)`/`windowScene(_:performActionFor:)`/`buildRootInterface*`/`makeRootView`/`shellHostingController`/`startAppearanceObserver`/`currentUserInterfaceStyle` 全部手动 window 代码；`configurationForConnecting` 仅捕获快捷项、返回 `UISceneConfiguration(name:"Default Configuration", sessionRole:)` **不设 delegateClass**；`sceneDidBecomeActive/EnterBackground`→静态 `handleScenePhase`；`openURLContexts`→静态 `handleOpenURL`；`switchToMain/LoginInterface` 改发 `authStateChanged` 通知。保留 `sharedContainer`/`sharedMainContext`/`makeStubContainer`/`currentColorScheme`。
  - `Info.plist`：删手写 `UIApplicationSceneManifest`（SwiftUI 自动生成全屏 "Default Configuration"）。
- 验证：`read_lints` 两个文件均干净、全代码库 0 残留 `shellHostingController`/`makeRootView`/`buildRootInterface`/`currentUserInterfaceStyle` 引用。命令行 `xcodebuild -destination 'iOS Simulator'` 因项目 `MACOSX_DEPLOYMENT_TARGET=26.5` 被解析成 mac 设备构建失败（storyboard "mac" + MessageUI 不可解析），属环境限制；请在 Xcode GUI 用 AIA scheme + iPhone 17 Pro 模拟器 Run 验证黑边是否消失。

## 外观模式（浅/深/跟随系统）切换失效修复（2026-08-13 落地）

### 现象
设置页「外观模式」三个选项（跟随系统/浅色/深色）点了完全没反应，界面不切换。

### 根因
`.preferredColorScheme(AppDelegate.currentColorScheme)` 挂在 `MainOrLoginView` 上，而 `currentColorScheme` 是读 `UserDefaults` 的 **static 计算属性**，SwiftUI 不感知它的变化，设置页改了 `@AppStorage("aia.appearance")` 后整窗不重渲染。ContentView 上基于自身 `@AppStorage` 的那层 `.preferredColorScheme` 虽能响应，但设置页是 push 上去的子页面，覆盖不稳定。

### 修复（AIAApp.swift + ContentView.swift）
1. **AIAApp.swift**：`body` 里加 `@AppStorage("aia.appearance") private var appearanceRaw = "system"`，把 `.preferredColorScheme(AppearanceMode(raw: appearanceRaw).colorScheme)` 挂到 **`RootView()` 上**（WindowGroup 闭包内的最外层 View）。`@AppStorage` 响应式，任一页面改值整窗立即重渲染。
2. 踩坑：`.preferredColorScheme` 是 **View 修饰符**，`WindowGroup`（Scene）没有该方法 → 编译报 `WindowGroup<some View> has no member 'preferredColorScheme'`，必须挂在 View 上而非 Scene 上。
3. 移除 `MainOrLoginView` 上依赖 static 的 `.preferredColorScheme`，以及 ContentView 里已无引用的 `appearanceRaw` / `appearanceColorScheme` 重复副本（避免未使用警告）。`AppDelegate.currentColorScheme` 定义保留但不再被引用（无害）。

### 验收
用户确认「搞定了」——切换即时生效。

### 教训
- 外观/主题这类全局 override，统一挂到 App 根 View（WindowGroup 闭包内最外层），用一个 `@AppStorage` 驱动，最稳；别分散挂在依赖 static 属性的中间层。
- `.preferredColorScheme` 是 View 修饰符，不能挂 Scene（WindowGroup）上。

## 云同步「彻底关闭 + 会员到期停掉」改造（2026-08-13 落地）

### 背景（用户决策）
- App 未发布、无老用户，所有新装用户都是"新用户"。
- 用户（开发小白，重隐私）要求：**默认不联网、不偷偷传数据**；且**会员到期后云同步也按同样标准彻底停掉**。
- 用户原话："有些用户比较注重信息安全，不希望数据同步云端"。

### 改动（CloudSyncManager.swift + RecordsViews.swift）
1. **`autoSync` 默认值 `true` → `false`**（上一轮已改）：新装用户默认关闭自动同步。
2. 新增统一放行属性 `static var canPerformCloudSync`：`autoSync && EntitlementManager.shared.can(.cloudSyncPush)`。
   - 复用现成权益接口 `can(.cloudSyncPush)`（plan 为 tester/paid/trial 才 true；**到期=.expired 即 false**）。
3. 三处调用点守卫由 `autoSync` 改为 `canPerformCloudSync`：`syncAfterLocalChange`（本地改动自动上传）、`syncAfterLogin`（登录/重装拉云端）、`backupIdentityProfile`（昵称/绑定码备份）。
4. `sync(context:)` 主流程加**中心化兜底**：开头 `guard canPerformCloudSync`，未放行直接 return，文案区分"自动同步已关闭"/"会员已过期，云同步不可用"。
5. `RecordsViews.swift` 健康页"从云端恢复数据"按钮：禁用判断改 `canPerformCloudSync`，置灰文案区分"自动同步已关闭"/"会员已过期"。

### 行为总表（彻底关闭后）
| 操作 | 结果 |
|------|------|
| 记数据→上传 | ❌ 不上传 |
| 冷启动/回前台/进后台自动拉 | ❌ 不拉 |
| 登录账号→拉云端 | ❌ 不拉 |
| 绑小程序→合并对方数据 | ❌ 不合并 |
| 注销账号→清云端 | ✅ 仍清（主动操作，与开关无关） |
| iCloud 备份 | ❌ 已关（独立 `icloudEnabled` 开关，默认 false） |
| 会员到期 | ❌ 同步彻底停（与关开关同标准） |

### 关键结论
- B 方案（字面彻底）已选：连登录/绑定都不碰云，数据完全留本地。
- 会员到期靠 `plan` 快照（启动/回前台 `refresh()` 拉取）本地判定；服务端 push 仍以 `sync_push_blocked` 兜底拒绝，双保险。
- `read_lints` 全部 0 报错。

## HealthKit 路线 B 落地：只读 + 自动值落 .hk 槽位（2026-08-13 用户拍板）
### 决策（用户 2026-08-13 明确）
- **App 只读 HealthKit，绝不回写**（删除了 HealthManager 的 `saveSteps/saveCaloriesConsumed/saveWeight/saveHeight/saveHeartRate` 全部回写函数，以及 ChatView/RecognitionSaver/ResultConfirmView 里所有 `saveXxx` 调用）。
- 手动健康数据存 `ManualHealthStore`（UserDefaults），**不在 SwiftData 的 HealthMetric 表**（HealthMetric 只存体检/体重长期记录）。
- 同一天「手动 + HealthKit 自动」如何记录：用 `.hk` 后缀 key 物理隔离，来源开关（`HealthMetricKind`×`HealthSourceMode`，存 @AppStorage `aia.health.source.xxx`）选展示谁，互不覆盖。

### 改动清单
1. **ManualHealthStore.swift**：
   - 新增 `enum HealthSource { manual, healthKit }`；`key(_:date:source:)` 增加 source 参数（默认 manual，老调用无损）。
   - 新增 `setHealthKitValue(_:metric:for:)` / `healthKitValue(_:for:)` 写读 `.hk` 槽位（覆盖式、幂等）。
   - 云同步 `exportModified` 不改（只遍历手动 key，`.hk` 天然不被上云 → 遵守「HealthKit 派生值不外传」铁律）。
2. **HealthManager.swift**：10 个 fetch 回调里调 `persistHealthKit(metric:value:date:)` 落 `.hk`；`tdeeActual(for:)` 字典优先 + 回落 `.hk`；删 save*；注释改「只读，不回写」。
3. **RecordsViews.swift / ChatView.swift / WidgetSnapshot.swift / UIComponents.swift**：自动模式展示逻辑从读易失内存 `health.xxx` 改为读 `ManualHealthStore.shared.healthKitValue(...)`（落库后持久化、跨天/回前台/跨进程一致，与手动模式同源）。
4. **bug 修复**：`RestingHeartRateInputSheet` 自动模式本可手改调 `saveHeartRate`（已删）；auto 模式按钮已禁用弹窗，移除该死分支。

### 铁律（防回归）
- 任何「写入 HealthKit」的调用都**禁止新增**；HealthKit 只进 ManualHealthStore 的 `.hk`，再经来源开关展示。
- `.hk` 槽位**永不**进云同步（避免多设备互相覆盖 HealthKit 派生值）。
- `read_lints` 全部 0 报错。
