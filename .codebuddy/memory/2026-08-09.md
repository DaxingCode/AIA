## 营养库「燕麦粥」被错配成「粥」的根因与修复
- 现象：语音/Siri「吃了一碗燕麦粥两个鸡蛋」→ 拆成 2 条正确，但食物名被记成"粥"而非"燕麦粥"（68kcal 错成 46kcal）。`parseFoodItems` 拆条正确，问题在营养库匹配。
- 根因：`NutritionLibrary.match` 第①步精确匹配 `FoodMetaStore.peek("燕麦粥")` 若未命中（设备 seed 缺失/normalize 不一致），掉到第③步 `searchSubstring` 子串匹配；其排序规则"靠后优先"使"粥"(在"燕麦粥"中位置1) 排在 "燕麦粥"(位置0) 之前 → 截胡父词。
- 修复（已落地 `NutritionLibrary.swift` `searchSubstring`）：排序新增两维度——①精确命中(tk==key)最高优先；②当 tk 是 key 的严格子串(tk.count<key.count) 判为"尾部碎片"降为最低优先（非碎片>碎片），再走原"靠后优先/同位置取更长"。验证："燕麦粥"场景精确命中胜出；"猕猴桃酸奶"等长词套短词场景仍靠后优先取"酸奶"，行为不变。
- 旁注：SEED_VERSION=4，seedBuiltin 覆盖式灌库，只要"燕麦粥"在内置表即会落库；但无论 seed 是否到位，子串修复都是根治（云端沉淀短名同样会触发截胡）。

## 「燕麦粥→粥」真机仍复现：内存内置表兜底（根治，不依赖 seed）
- 现象：上文 v6 seed + `searchSubstring` 排序修复 + 双路径补刀**装真机后仍显示「粥」**。根因：真机当前运行包里本地库 `FoodMetaStore` 仍缺「燕麦粥」精确条（老设备跳 seed 或补丁前版本残留），导致：
  - `upgradeFoodNameIfNeeded` 只看 `FoodMetaStore.peek("燕麦粥")` → nil → 不升级；
  - 旧 `NutritionLibrary.match` 只在 `allNames.isEmpty`（库**全空**）时才回退内存表，老设备库非空（有旧「粥」），不触发回退，反而 `searchSubstring` 让短词「粥」胜出。
- 修复（根治，已落地）：
  1. `NutritionLibrary.match`：把内存回退从"仅库全空"扩为"库命中**严格子串碎片**时也回退查 `table` 精确长词"。即 `ref.name` 是 key 的严格子串（如 key=燕麦粥 命中库里"粥"）且 `table[key]` 存在 → 返回内存精确条。内存内置表永远有「燕麦粥」，不依赖本地库 seed 是否到位。
  2. `ChatView.upgradeFoodNameIfNeeded`：判断是否升级的依据由 `FoodMetaStore.peek` 扩为 `NutritionLibrary.shared.match(...) != nil || FoodMetaStore.peek != nil`，借 match 的新兜底命中内置长词。
  3. 图片/快捷指令路径走 `LocalQuickParse`/`canonicalFoodName`（内部调 `match`），自动受益。
- 关键区别：之前修复假设"seed 后库必有精确条"；本修复**彻底绕开 seed 依赖**——即使老设备本地库永远缺条，内置长词也永不退化成短词。用户必须重新 build 安装新包才生效（真机跑的是旧 match 逻辑）。

- 铁律：**凡从本地营养库（FoodRef/NutritionLibrary/FoodMetaStore）取每100克值组装 FoodPayload 的入口，都必须 × (重量÷100) 缩放到这份总量**；云端视觉模型（返回已是这份总热量）不要乘。
