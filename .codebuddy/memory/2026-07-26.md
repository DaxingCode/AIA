## 对话页麦克风按钮震动（UIImpactFeedbackGenerator 被 AVAudioSession 吞掉的根因与定稿）
- 现象：真机（iPhone15PM, iOS26.52，系统触感已开）开麦无震动、关麦有；首页语音按钮有。
- 根因：`recognizer.start()`（VoiceRecordView.swift:62-76 beginRecording）→ `AVAudioSession.setActive(true)` + `AVAudioEngine.start()` 是**同步激活录音会话**，会挤掉紧随其后的 Taptic 渲染；关麦 `stop()` 只 `setActive(false)` 无"激活"重动作，故正常。
- 关键差异：关麦触觉在 `stop()` 之前同步触发；开麦无论触觉放在 `start()` 前（初版）还是后（delayed 版）都紧挨同步音频激活 → 被吞。
- **定稿写法**（ChatView.swift 麦克风按钮 + 自动开麦 onAppear 两处统一）：按下先 `UIImpactFeedbackGenerator(style:.medium).prepare()+impactOccurred()` 立即同步触发（与关麦同款时机），再 `DispatchQueue.main.asyncAfter(+0.1){ recognizer.start() }` 把录音会话激活推后 100ms。体验上=震动先响=告知用户已开始，再开麦说话。
- 兜底预案（未用）：若 iOS26.52 录音会话激活期间全局抑制 UIImpactFeedbackGenerator，改用 `AudioServicesPlaySystemSound(kSystemSoundID_Vibrate)`。先验证当前版。
- 注：模拟器无 Taptic Engine 不会真震，须真机验证。

## 昵称云端同步（本会话新增需求）
- 需求：已登录用户修改昵称 → 同步云端；后续再登录 app → 直接展示修改后的昵称。
- 现状：昵称是 `@AppStorage("userNickname")`（默认"阿宝的朋友"），MyAccountView 注释原写"仅本地保存"；`userName`(Keychain) 是登录名不可改，昵称同步走 `userNickname`。
- 方案：把昵称当一条 `type:"profile"` 的伪记录，复用现有 aia_records 同步通道（符合"一切经 aia_records"约定）。**云函数 aia-sync 是泛型的（push 收任意 type、pull 按 userId 返回全部），无需改云端，仅更新了注释**。
- 改动点：
  - `CloudSyncManager`：`buildPushItems` 在 `userNicknameUpdatedAt > sinceTime` 时附带 profile 记录（固定 id `9F2B4C7E-...-0F33`，因 push 以{id,userId}唯一、pull 按 userId 过滤，固定 id 即可 upsert 同一条）；`pull` 新增 `case "profile"` → `applyProfile`（仅当云端 updatedAt 晚于本地才覆盖，后写胜出）。
  - `MyAccountView`：`@AppStorage("userNickname")` 加 `.onChange` → 写 `userNicknameUpdatedAt=now` 并 `syncAfterLocalChange(context:)`（内部已守卫未登录不推送）；提示文案改"修改后会同步到云端，换设备登录沿用"。
  - 注意 `UUID(namespace:name:)` 在此 SDK 不可用 → 改用固定 UUID 常量作 profile 记录 id。
- 行为：改昵称触发 3s 防抖增量同步上云；登录走 `syncAfterLogin`(先 pull 后 push) 自动回写 userNickname（UserDefaults 写入会被 `@AppStorage` 观察到，首页/记录页实时刷新）。UserDefaults 不随重装保留，但 Keychain 保留 userId，重装后登录仍可从云端拉回昵称。
- 编译 `BUILD SUCCEEDED`。改动尚未提交（用户未要求）。

## 云端冒烟测试暴露真正根因（重要）
- 用 curl 直打 `https://cloud1-...ap-shanghai.app.tcloudbase.com/recognize`（`mode:queryFood`）：返回 `ver:20260726a-queryfood-relax`（确认部署的是新包）但 `ok:false, error:"缺少 imageBase64 或 text"`。
- **真因**：`recognize/index.js` `main()` 第 504 行 `if (!body.imageBase64 && !body.text) return 报错` 在 queryFood/greeting 分支**之前**早退。而 queryFood（只带 foodName）、greeting（只带 context/userId）本来就**没有** imageBase64/text → 永远先撞 504，到不了各自 handler。
  - 也就是说：联网搜索从一开始**从未真正连通云端**（App 之前显示的"未找到"其实是这个错误被当通用未找到）；云端招呼语同样一直静默失败，只是 App 有本地兜底（`agentChatGreeting` 失败走 `buildGreeting()`）所以用户没察觉。
  - 之前那版 prompt 放宽（a 包）治标不治本——路由不通怎么都查不到。
- **修复**：第 504 行改为 `const needsImageOrText = body.mode !== 'queryFood' && body.mode !== 'greeting'; if (needsImageOrText && !imageBase64 && !text) return ...`，对两个纯文本模式放行（agent/chat 仍需 text 不受影响）。
- **重新打包**：`recognize-20260726b-queryfood-route.zip`，FN_VERSION=`20260726b-queryfood-route`。用户已部署 b 包。
- **b 包复测暴露第三层问题**：curl 复测返回 `ver:20260726b`（路由已通）但 `error:"未能解析营养数据"`。根因：`handleQueryFood` 误用了 `extractJSON()`——该函数是**图片识别专用**，强制要求 `types` 数组字段，缺失就丢弃解析结果返回 `{types:['none']}`。营养 JSON `{name,calories,...}` 没有 types → 即使模型返回完美 JSON 也必然失败。**queryFood 用 extractJSON 永远不可能成功**。

## 首页编辑态「今日事项预览」横向变短修复（本会话）
- **现象**：进入首页编辑态，「今日事项预览」卡片只占左半格（约一 tile 宽），期望像正常态那样跨满整行。

## 修复：Siri「喝了100毫升水」误记成 100 元账单
- 现象：跟 Siri 说「喝了100毫升水」→ 同时出现 100 元账单 + 100 毫升水两条记录。
- 根因（LocalQuickParse 上一轮回归）：`parseBill` 的 `mealWords` 含「喝」，且 `firstAmount` 正则货币单位可选 → 把「100毫升」的 100 当 100 元建档（聊天页 `createBillLocally` 有 `hasMoneyUnit` 护栏，Siri 这条漏了）。
- 三处修复（BUILD SUCCEEDED）：
  1. `LocalQuickParse.parseBill`：账单必须带货币单位（元/块/￥/¥），`isFoodWithAmount = hasMeal && hasMoneyUnit`，与聊天页对齐。
  2. `LocalQuickParse.parseFood` 开头：`if WaterIntakeParser.parse(text) != nil { return nil }`，纯饮水句不抢食物分支。
  3. `TellAIAIntent.perform` 饮水快捷前置：先算 `waterParsed` 与 `localResult`；`waterParsed!=nil 且 localResult==nil`（纯饮水句）直接记水并 return，彻底不碰云端；复合句（水+账单）记水后继续走账单流程。`localResult` 只算一次复用。
- 教训：LocalQuickParse 任意新分支都要对齐聊天页护栏（货币单位 / 纯饮水放行），否则 Siri 链路会回归。
