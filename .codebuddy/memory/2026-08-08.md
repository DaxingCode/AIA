## 账单导入功能 — 方案 B 完整落地（微信 xlsx + 支付宝 csv）

### 背景
用户给了微信支付「下载账单」官方 `.xlsx` + 支付宝「交易明细」`.csv`，原 `BillImportView.parseCSV` 只认英文/固定列头模板且用 `String(contentsOf:)` 读文件，两文件都无法识别。方案 B：引入 xlsx 解析 + 微信/支付宝适配器 + 导入判重（用户要求）。

### 新增文件（均在 `AIA/AIA/`）
1. **`BillFileReader.swift`**：零第三方依赖。xlsx = zip（`xl/sharedStrings.xml`+`xl/worksheets/sheet1.xml`），用 `Compression` 框架 `compression_decode_buffer(ZLIB)` 手动 inflate（扫 PK\x03\x04 local file header 按文件名定位），`XMLParser` delegate 解析成二维 `[[String]]`（SheetParser 按 `r="A1"` 列引用定位列，`inlineStr` 与 `t="s"` 共享索引都处理）。csv 用 utf8 失败回退 `CFStringEncodings.GB_18030_2000`（支付宝旧版 GBK），按行 split 容错、跳水印/空白行，靠「含交易时间」定位表头行。输出 `BillRawFile(source:.wechat/.alipay/.unknown, rows:)`。
2. **`BillImportAdapter.swift`**：`BillRawFile` → `[ImportableBill]`。列定位全用「包含关键字」容错（时间/收支/分类/金额/商户/备注），不写死列序。微信：`收/支`→`isIncome`（收入/转账收入/退款=true）；支付宝：跳过前 23 行水印、表头第 24 行、`不计收支`整行丢弃、`交易状态`非成功跳过、`金额(元)`纯数字直转。

- `fileImporter` 的 `allowedContentTypes` 加 `UTType(filenameExtension:"xlsx")`。
- `handleFileImport` 按扩展名分流：xlsx/csv → `BillFileReader.read` → `BillImportAdapter.adapt`（传 `self.parseDate`）；纯文本仍走 `parseCSV` 兜底。新增 `importFromFile`/`adaptAndSet`。
- `parseDate` 增加 **Excel 序列号支持**（微信 xlsx 时间是 Excel 日期序列号如 46241.45，按 `(serial-25569)*86400` 转 1970 时间戳），否则原字符串格式全失败。

## Siri 卡死 + 识别变慢 — 彻底根治（2026-08-08，两轮修复）
### 现象
Siri「午餐花了15元」「喝了200毫升水」→ Siri 一直转圈 + App 前台首页卡死动不了；且"之前快现在慢"。

### 根因（最终定位 = 互锁死结）
- 上轮仅加了 `skipCloudSync:true` 缓解云端 await，但**互锁根因未除**：
  `perform()` 在 `Task.detached` 后台跑 `processRecognition` → 内部 `performSilentSideEffects` 用 `await MainActor.run { HealthManager... }`。
  这个 `await` 要等主线程空闲；但同一次后台 `context.save()` 触发 `NSManagedObjectContextDidSaveNotification`，主线程 `@Query` 忙于合并新记录 → 腾不出手执行 MainActor.run → 后台等主线程、主线程等后台 save 推进 → **互相死锁**。表现即卡死 + 转圈不停，本地快析（毫秒级零网络）也被整体 hang 住显得"变慢"。
- 更深一层：Intent 用 `AppDelegate.sharedContainer`（与主 App 同一 container 实例），后台 `ModelContext.save()` 经 `automaticallyMergesChangesFromParent` 实时合并进 `sharedMainContext` 的 `@Query` → 前台首页重渲卡顿。

### 修复（4 文件，已落地 + xcodebuild 模拟器 BUILD SUCCEEDED + lint 0 错）
**A. 解互锁**：`RecognitionSaver.performSilentSideEffects` 改为 `private static func`（非 async），HealthKit 写入改 `Task { @MainActor in ... }` **fire-and-forget（不 await）**；`processRecognition` 内 `await performSilentSideEffects(...)` 去掉 `await`。
**B. 断合并（根治卡首页）**：`TellAIAIntent.perform()` 容器由 `AppDelegate.sharedContainer` 改为 `AppPersistence.makeSiriWriteContainer()`（新增，指向同一 `AIA.store` 但**不同 container 实例**）。SwiftData 的跨 context 合并按 container 的 parentContext 链传播，**不同 container 之间不自动合并** → 前台 `@Query` 永不被惊动 → 不卡首页。无论 App 前台/后台/冷启都走独立容器。
**C. 前台刷新**：`AppDelegate` 新增通知 `siriDidSaveData`；`TellAIAIntent` 三处写路径（纯水句 / 复合水句 / 识别入库）save 后主线程 `post(.siriDidSaveData)`；`ContentView` `.onReceive(.siriDidSaveData)` 调 `RecurringBillManager.generateDue` + 对 Bill/FoodEntry/Reminder/HealthNote 各 `context.fetch` 一次尽力刷新（跨容器不自动合并，后台/锁屏场景靠 App 回前台 `didBecomeActive` 或下次启动打开同一 store 自然读到）。

### 关键认知
- 之前"快"是因为 `perform()` 直接 `@MainActor` 同步跑、HealthKit 同步占主线程但不互锁；改 `await MainActor.run` 反而造死锁——互锁比"占主线程"更致命。
- 纯饮水句走 `WaterIntakeParser` 本地零网络、不进 `processRecognition`，也秒回。

## 群发通知「点发送无反馈」真机排查 + 3 处云函数 SDK 语法 bug 修复（2026-08-08）
### 现象（真机 DEBUG 包）
开发者中心 APNs 推送页点发送：页面无 toast 反馈、也收不到通知。Xcode 控制台关键两行：
`body={"ok":false,"error":"broadcast failed: _.doc is not a function"}`
`[Announcement] broadcast 云端返回失败: ["error": broadcast failed: _.doc is not a function, "ok": 0]`
同时确认数据链路健康：`listDevices` 返回 `total:2 users:[{userId:"apple_000466...",count:2,envs:["sandbox"]}]`；`registerDevice 上报成功 env=sandbox → aia_devices 已写入`。

### 根因（3 处 wx-server-sdk 非法 API 调用，已修复 `云函数/aia-sync/index.js` 并重新打包 `aia-sync-20260808.zip`，需上传 CloudBase 重新部署）
1. **`handleBroadcast` count 查询致命**：`db.collection(DEVICES_COLLECTION).where(_.doc('_id').exists(true))` —— `_.doc(...)` 在 db.command 里**不存在**（仅 `_.eq/_.in/_.exists` 等命令），执行即抛 `_.doc is not a function`，被 catch 接住返回 `ok:false`。修复：查全部直接 `db.collection(DEVICES_COLLECTION)`（不加 where）；按 userId 过滤改为 `.where({ userId: _.in(arr) })`。
2. **`handleBroadcastTick` 取设备同样非法**：`_.in(job.userIds, 'userId')` + `_.doc('_id').exists(true)`。修复：`.where({ userId: _.in(job.userIds) })`；查全部 `db.collection(DEVICES_COLLECTION)`。
3. **完成回执查错集合**：`db.collection(DEVICES_COLLECTION).doc(job.submitterDeviceId)` —— `submitterDeviceId` 是 token hex，但 `aia_devices._id` 是 `userId_deviceId`，永远查不到→回执发不出。修复：`.where({ token: job.submitterDeviceId }).limit(1).get()` 取 `[0]`。

### 关键经验（写进长期记忆）
- **wx-server-sdk 查询口径**：「查全部」= 直接 `db.collection(x)` 不加 `.where()`；「按字段过滤」= `.where({ field: _.in(arr) })`（注意 `_.in` 第一个参数是数组、第二个是字段名写进对象 key，**不是** `_.in(arr, 'field')`）；`_id` 存在性 = `.where({ _id: _.exists(true) })`，没有 `_.doc()`。
- 真机 token 上报健康（listDevices 能查到）→ 收不到推送优先查云函数日志的查询语法/异常，而非 App 端。

### 二次修复（同次真机复测，已修 + 重新打包 `aia-sync-20260808.zip`）
- 部署首个修复后复测：`_.doc is not a function` 消失，但报 `-502005 database collection not exists: aia_broadcast_jobs`。根因：`aia_broadcast_jobs` 集合从未在 CloudBase flexdb 建过（用户此前只手动建过 `aia_devices`），wx-server-sdk 对不存在的集合 `.add()` 直接报错（不自动建表）。

- 经验：**新集合首次使用需先 `db.createCollection`**，否则 `.add()/.get()` 报 `-502005`；或在 CloudBase 控制台手动建表也行。

### 三次修复（job 卡 pending 不发送，已修 + 重新打包 `aia-sync-20260808.zip`）
- 复测：建表后 `handleBroadcast` 返回 `accepted=2`、job 已写入，但 job 永久卡 `status:pending/sent:0/cursor:0`，收不到推送。

- 验证待真机：预期日志 `[broadcast] 首轮 tick 结果 {"ok":true,"done":true,"sent":2}`、记录页 job 变已完成、真机收推送+「✅ 推送完成」回执。若仍失败看 `broadcast tick failed:` 字样（大概率是 APNs JWT/PEM 环境变量）。

## 食物照片「碗/个/片 → 克」换算增强（2026-08-08，BUILD SUCCEEDED）
### 背景
照片识别（云端视觉模型 Qwen-VL）对食物只回 `portion`（如「1碗/1个/1片」），不回克数。旧逻辑：含「克/g」→ 取真实克数；否则兜底 100g，丢失估算。更严重 bug：①确认页用 `#"\d+"#` 抓首个数字，「1碗」被提成 `1` 克；②模型给的是「该份量总营养」，旧逻辑当「每100g」再乘 weight/100，把 1碗→150g 时热量被放大 1.5 倍。
### 已落地改动（3 文件，BUILD SUCCEEDED + lint 0 错）
1. `RecognitionSaver.swift`：新增 `servingUnitGrams` 换算表（碗150/碟100/盘200/份120/个100/颗100/只100/枚100/片30/块50/根80/条80/杯240/瓶500/罐330/勺15/匙15/把50/串80/瓣5/口25/张40/粒5/尾120）+ `weightFromServingUnit(_:)` helper（仅 weightFromPortion 未命中时调用）。`autoSave` 食物入库：`weight = weightGram ?? weightFromPortion ?? weightFromServingUnit ?? 100`，并把模型总营养反推每100g基准（`per100 = 100/weight`，base* = 总×per100，entry 总营养 = base×ratio = 模型原估算），消除热量伪增。
2. `ResultConfirmView.swift`：修复「1碗→1克」bug，构建 EditableFood 时 weight 走 `weightFromPortion ?? weightFromServingUnit ?? 100`，caloriesPer100g 等 = 模型总营养 × per100（applyAndSave 单/多分支自动继承，口径与 autoSave 统一）。
3. `ResultRowCard.swift`：对话页待确认卡保存 `commitEntry` 的 weight 链补 `weightFromServingUnit`（base* 反推本就正确，无需动）。
### 效果
「1碗米饭」→ 重量150g、热量=模型估算值（不再 1g、不再放大）；营养表(每100g)/显式克路径数值不变（ratio=1 等价）。换算表为经验均值，用户可在详情页手动改。

`xcodebuild` 模拟器完整构建 `BUILD SUCCEEDED`，3 文件 lint 0 错。
