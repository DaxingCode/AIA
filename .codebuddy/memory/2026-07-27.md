## saveData 修 InvalidDoc 致命 bug（2026-07-27）
- 现象：小程序记水 → `aia_records` 无 type:water，saveData 日志报 `-501007 InvalidParameterValue.InvalidDoc document illegal`。
- 根因：`mapMealToPayload`/`mapWaterToPayload` 里 `ts = Math.floor(new Date(dateStr+'T...').getTime()/1000)` —— 当 `rec.date` 为空时 `new Date('T00:00:00')` 是 Invalid Date，`getTime()` 返回 `NaN`，而 `Math.floor(NaN)` **不抛异常** → `payload.date=NaN`。TencentDB 拒绝 NaN 字段值 → InvalidDoc。meal 当时带 date 所以没触发，water 的 `currentDate` 为空触发。
- 修复：`try` 内先取 `d=getTime()`，仅 `isFinite(d)` 才写 `ts`，否则保留 `Math.floor(Date.now()/1000)` 兜底（绝不写 NaN）。两个 map 函数都修。
- 附带 bug：前端 `addDrink` 传 `ml`，云函数读 `rec.amount` → 水量恒为 0；改 `mapWaterToPayload` 优先 amount、缺失取 ml。
- 双保险：water 分支 `.set` 失败自动回退 `.add()` 并打诊断日志（区分 docId 非法 vs body 非法）。改完需重新部署 saveData 到 cloud1 验证。

## 刷新后饮水/饮食记录消失（日期格式不匹配）
- 现象：小程序点"喝一杯水"立即显示，但刷新小程序后记录消失（写入成功、读回失败）。
- 根因：`records.js` 的 `currentDate = this.formatDate(now)` = `"2026年7月27日 星期一"`（中文显示串，带星期），同时用作 loadData 的 `date` 入参与 saveData 记录 `date`。而 `loadData` 的 food/water 分支过滤 `w.date === date`，`w.date` 来自 `fromFoodPayload/fromWaterPayload` 把 `payload.date` 时间戳转成的 **`YYYY-MM-DD`**。两格式不一致 → aia_records 记录被 filter 全部排除 → 刷新即丢。food 分支、week avg（`_loadWeekAvg` 也传中文串）同理受影响。
- 修复：`loadData` 新增 `toYMD()` 把中文/YYYY-MM-DD 都归一为 YYYY-MM-DD，用于 meals+water 两处 filter。`saveData` 新增 `parseDateToTs()`，正确解析中文日期串为 Unix 秒（之前中文串 `new Date()` 解析为 Invalid Date → 回退 `now`，导致切到过去日期加水时 payload.date 错误）。两个文件都要重新部署 cloud1。
- 结论：前端 `currentDate` 同时承担"显示串"和"数据 key"双重角色是隐患根源；本次用云函数侧归一化兜底，未改前端。

## 图片重复识别准确率优化（BUILD SUCCEEDED，未 commit）
- 背景：原去重只用 `ImageHasher.aHash`（8×8 平均哈希），对亮度/对比度/状态栏时间极敏感 → 同图漏判、异图误判。
- `ImageHasher`：新增主指纹 `fingerprint(_:)` = 裁状态栏/底部噪声(`cropNoise` 顶10%/底4%)后做 `dHash`（9×8 差异哈希，对亮度/对比度/gamma 免疫，64bit）+ 返回 `ratio=宽/高`。`aHash` 保留作参考未删除。
- `DuplicateStore`：① `DuplicateEntry` 字段 `hash`→`hashD`+新增 `ratio:CGFloat`，自定义 `init(from:)` 兼容旧 aHash 字段（`hash` 解码兜底为空串，旧图首次 load 因 decode 失败回 [] 清库属可接受），并附显式 `encode(to:)` 只编码真实属性（避免 `hash` 无对应存储属性导致 Codable 失败）；② `match(_:ratio:)` 增加 `abs(e.ratio-ratio)<0.05` 比例校验过滤不同尺寸/裁切图降误报；③ 阈值 `10`→`8`（dHash 更稳可收紧）；④LRU：`add` 超出 `capacity=500` 丢最旧。
- 调用点：`RecognitionSaver.processRecognition`（两处）与 `ResultConfirmView` 全部 `ImageHasher.aHash`→`fingerprint`，`DuplicateStore.match(hash)`→`match(fp.hash, ratio: fp.ratio)`，`DuplicateEntry(hash:...)`→`(hashD:ratio:)`；`DuplicatePayload` 增 `ratio` 字段并透传，避免确认页回写指纹时比例被 0 覆盖。
- 验证：`xcodebuild` 模拟器 BUILD SUCCEEDED。行为：仅"似乎已记录过"警告横幅，不阻断入库，优化目标是降误报/漏报。

## App 同步 HTTP 413 修复（2026-07-27 续3）
- 现象：App 同步提示「请求失败（HTTP 413）」。413=请求体过大，来自云函数 /sync 的 HTTP 触发网关层 body 大小上限。
- 根因：`CloudSyncManager.push` 把 `buildPushItems` 的全部记录一次性打包 POST（首次/登录后全量同步 since=nil 时发送所有本地记录），请求体过大 → 413。pull 请求体仅含 userId+since 很小，不会 413。
- 修复：`push` 改为分批发送（batchSize=50，stride 切片，每批独立 postJSON，累加 upserted 返回）；云端按 {id,userId} upsert 幂等，分批中途失败重发安全。另把 postJSON timeoutInterval 30→60，防大数据量 pull 响应超时。
- 验证：xcodebuild iPhone 17 Pro 模拟器 BUILD SUCCEEDED；CloudSyncManager lint 全清。
- 未做：pull 响应体理论上也可能超 API 网关 6MB 响应上限（仅当用户跨端数据量极大），当前未分页；若用户后续报 pull 慢/超时再在云函数 + 加游标分页。
