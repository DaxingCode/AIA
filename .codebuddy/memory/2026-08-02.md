## 发图后图片不立即展示、等识别完才和结果一起出现 — 修复
根因：ChatView 消息列表是**手动 fetch 的 @State（`fetchMessages()` 写入），非 @Query 响应式**。图片气泡靠 `appendUserImageMessage` 在 `runImageRecognition` 开头 `insert`，但当时不广播刷新；输入栏的「正在识别」是 `RecognitionActivity.shared.isRecognizing` 单例提示（另一条机制），所以发图瞬间就亮。直到识别完成 `RecognitionSaver.processRecognition` 的 `save` + `post("AIA.chatScrollToBottom")` 才让 ChatView 刷新，于是被 insert 很久却没刷新的图片气泡和刚插入的结果卡在同一次刷新里同时冒出。

## 对话页多选删除"点了没反应、内容仍在" — 修复
根因：`ChatView.deleteSelectedMessages()` 在 `for` 循环调用 `SafeDelete.chatMessageByID(id, in:)` 之后**立即同步**调 `fetchMessages()`。但 `SafeDelete.chatMessage` 内部把所有软删操作包在 `DispatchQueue.main.async` 延迟执行（为详情页转场动画设计的保护）。于是 fetch 跑时 `syncDeleted` 仍是 `false`，把待删消息又读回；之后 main.async 才标记删除，却无人再触发刷新 → 页面停原样。
修复：`deleteSelectedMessages` 先同步退出多选模式（底部条立即隐藏），再把"逐个标记 syncDeleted + fetchMessages()"整体放进 `DispatchQueue.main.async`，保证软删先生效、再按 `!syncDeleted` 过滤拉取。lint 0 错。
注意：这是 `SafeDelete.*ByID` 一律 `main.async` 与 `fetchMessages()` 手动 fetch 非响应式叠加导致的时序坑，后续任何"软删后立即手动 fetch"场景都要同理延后。

## 对话页删除消息后时间戳"增多" — 修复（第一轮：只减不增）
现象：删掉多条消息后，连续出现多个时间戳（18:49/19:10/20:24/20:36 等），间隔其实都 < timeDividerGap(5min)，本不该这么多。
根因：`dividerFlags(for:)` 旧逻辑用「与上一条相邻消息比较」：`list[i].createdAt - list[i-1].createdAt > gap` 才显示。删除中间消息会让原本相邻间隔 < gap 的两条变成间隔 > gap，从而触发新时间戳——表面上"删了消息时间戳反而多了"。
修复：`ChatView.swift` 的 `dividerFlags` 改为「与上一条已显示时间戳的消息比较」（`lastShowedAt` 初值=首条，命中 gap 才更新）。时间戳分段锚点只减不增：删消息后不会再补出时间戳，新消息/加载更早历史仍正常分段。lint 0 错。

## 对话页删除消息后"残留孤立时间戳（无对应消息）" — 综合修复 A+B+C+D（第二轮）
现象：删掉图片消息 / 文字消息 / 阿记回的识别卡片消息后，时间戳**立刻残留**且永久不消失，中间没有任何消息气泡。
根因四面向（任一根因都可能造成该表象，故综合修复）：
- A 渲染层：时间戳渲染 `if showDivider[idx] { ChatTimeDivider }` 未校验该消息是否仍可见（软删、空壳卡），导致软删消息的时间戳仍被画出。
- B 计算层：`dividerFlags` 对 `displayedMessages` 整段算，但空壳识别开场白/空 items 识别卡在 `displayedMessages` 里被过滤掉，其"首条永远 flags[0]=true"语义若落在被过滤项会错挂；需对"可见消息"做分段守门。
- C 删除时序：`SafeDelete.chatMessage` / `chatMessageByID` 内部用 `DispatchQueue.main.async` 标记 `syncDeleted`，但调用点（单条 `onDelete`、批量 `deleteSelectedMessages`）同步或同层 `fetchMessages()` 与软删竞态，可能读回未标记消息、或标记后无刷新 → 时间戳残留。
- D 兜底：理论 `fetchMessages` 已带 `!syncDeleted`，但 `displayedMessages` 拼接 `greetingMessage`、状态竞态边界下仍可能漏。
落地（ChatView.swift，lint 0 错）：
- 新增 `static messageProducesVisibleContent(_:)`：软删、空壳识别开场白、空 items 识别卡返回 false（复用 recognitionCache + decodeRecognitionPayload）。
- A：`messageList` 渲染改为 `if showDivider[idx], !m.syncDeleted, Self.messageProducesVisibleContent(m) { ChatTimeDivider }`。
- D：`displayedMessages` 末尾 `limited.filter { !$0.syncDeleted }` 兜底。
- C 单条 `onDelete`：`SafeDelete.chatMessage(...)` 后 `DispatchQueue.main.async { fetchMessages() }`；批量 `deleteSelectedMessages` 内层 for 标记后再嵌套 `DispatchQueue.main.async { fetchMessages() }`（因 chatMessageByID→chatMessage 嵌套两层 main.async，需再延一层确保排在其后）。

## 待办列表「上下滚动」与「长按拖拽改期」不能共存 — 方案 B 修复（BUILD SUCCEEDED）
现象循环：挂 `.simultaneousGesture(drag)` → 滚动失效；改成 `.gesture(drag, including: longPressArmed ? .gesture : [])` → 滚动恢复但长按后拖不动。
根因（重要通用坑）：**`.gesture(_:including:)` 的 `including:` 只在视图构建时求值一次**。长按前 `longPressArmed=false` → drag 以空 mask `[]` 挂上；长按成立把 @State 改 true 并不会让 `including:` 在**同一次 touch 序列**里重新求值，drag 始终是空壳，改期拖动永远接不上。
正确范式：**手势始终挂载（`.gesture(drag)`），用 `onChanged` 首行 `guard` 决定是否消费事件**。未长按时直接 return → 不 claim 事件 → ScrollView 滚动 100% 正常；长按成立后同一次 touch 的后续移动被这个并行 recognizer 实时收到 → 进改期逻辑。
落地三处：
- `SelectableRowModifier.swift`：`SelectableRow` 新增 `var disableSwipe: Bool = false`；内部 `.simultaneousGesture(dragGesture, including: disableSwipe ? [] : .gesture)`。这里用 `including:` 是安全的——长按成立会触发重绘，且左滑手势本轮本就不该参与。其余 4 处调用方不传 → 行为不变。
- `RecordsViews.swift` `todoRow`：drag 的 `onChanged` 首行 `guard longPressArmed, !multiSelectMode else { return }`（原 `if !multiSelectMode {}` 块拆平）；`onEnded` 同样加 `guard longPressArmed else { return }`（drag 始终挂载 → 普通滚动松手也会走 onEnded，不加守卫会误清其他行拖拽状态）。
- `SelectableRow(...)` 调用加 `disableSwipe: longPressArmed`，长按后摘掉左滑，避免水平拖动同时误露「删除」按钮。

## 对话页「旧时间戳消失、又冒出新的时间戳」— 第三轮修复（计算层与渲染层口径对齐）
现象：之前删消息后时间戳"增多"问题经第一/二轮（只减不增 + messageProducesVisibleContent 守门）缓解，但用户实测：**旧时间戳消失的同时，在某条消息上又出现一个新时间戳**。
根因：`dividerFlags` 与渲染层守门口径**不一致**——渲染层用 `showDivider[idx] && !m.syncDeleted && messageProducesVisibleContent(m)` 把"不可见消息"（空壳识别开场白、空 items 识别卡）剔除；而 `dividerFlags` 仍把所有 `displayedMessages`（含不可见项）纳入分段锚点：首条强制 `flags[0]=true`，循环用 `lastShowedAt` 跟随每一条（含不可见）。当不可见消息距上条 > gap 被 `dividerFlags` 标记后，**它更新了 `lastShowedAt` 却不被渲染层画出**，其后紧邻的真实可见消息因距这个"被偷走的锚点" > gap 又被误判需新时间戳 → 凭空多一个。
修复（ChatView.swift `dividerFlags`，BUILD SUCCEEDED / lint 0 错）：
- 首锚点从 `list[0]` 改为**第一条可见消息**（`messageProducesVisibleContent(list[i])` 命中即停）；整段不可见则全 false。
- 循环对 `!messageProducesVisibleContent(list[i])` 的 `continue`：既不打 flag、也不更新 `lastShowedAt`。分段基准只含可见消息，与渲染层守门严格对齐，不可见消息无法再偷锚点。
经验：**凡是"某消息是否显示时间戳"的计算与渲染，必须用同一个 `messageProducesVisibleContent` 判定，否则锚点基准混入不可见项就会错位**。
