- 根因：`recognizeWithLocalPriority` 中「单账单本地胜出」判断排在「营养成分表」判断之前。免费用户若本地 MerchantMeta 里有「0g」这类错误商户（来自之前误识别的超市小票），`localWins` 会返回 true，于是账单结果在营养成分表解析之前就被返回了。包装上的 `3.1g`、`12.0g` 等宏量数字被单账单金额正则误捕。
- 修复：`AIA/AIA/RecognizeService.swift`。
  - 把营养成分表本地解析提到单账单判断之前（步骤 2 → 步骤 2，单账单后移为步骤 3），食物包装优先被识别为食物。
  - 新增 `isWeightOrUnit(_:)` 静态 helper，识别 `400g`、`0g`、`件数` 等重量/规格/单位；
  - `extractMerchant` 的 `isValidMerchant` 排除重量规格；
  - `extractMerchant` 的 MerchantMeta 查询跳过重量规格 key；
  - `fuzzyCorrectMerchant` 的 known 库过滤排除重量规格商户，避免把「0g」这类脏数据当已知商户纠正。
- 验证：独立脚本 `/tmp/test_nutrition_yogurt.swift` 复刻营养成分表解析，对酸奶标签输出 `hasNutritionTable=true`、energy≈90.58 kcal、protein=3.1、carbs=12.0、fat=3.3、name=巴氏杀菌热处理风味酸奶；`xcodebuild` **BUILD SUCCEEDED**。
- 预期：免费/付费版拍同一瓶酸奶，都应识别为食物，显示约 90.6 kcal / 3.1g / 3.3g / 12.0g，底部提示「按包装标签识别」。

## 改进：营养库匹配「头名词优先」
- 需求：用户要求营养库匹配更聪明，如「猕猴桃酸奶」优先匹配「酸奶」而非「猕猴桃」（加工食品主体是被风味掩盖的基底，如乳制品/饮料）。
- 文件：`AIA/AIA/NutritionLibrary.swift`
- 旧逻辑：子串匹配取**最长**命中键 → 「猕猴桃酸奶」中「猕猴桃」(3字) > 「酸奶」(2字) 被选中，用水果营养值覆盖乳制品。
- 新逻辑：中文复合食物多「修饰语+头名词」，头名词通常在后，是营养主体。子串匹配改为**记录每个命中键在名称中的位置，优先取最靠后者；同位置再取较长键**。
  - 「猕猴桃酸奶」含 猕猴桃(0)/酸奶(3) → 酸奶；「香蕉牛奶」「草莓酸奶」同理。
  - 纯「猕猴桃」「苹果」仍精确命中，不受影响；「咖啡」精确命中「咖啡」键。
  - 名称是某键子串（如「咖啡」命中「美式咖啡」）作兜底，位置记最前（低优先）。
- 验证：独立脚本 `/tmp/test_nutrition_match.swift` 复刻新逻辑，**猕猴桃酸奶/猕猴桃风味酸奶/巴氏杀菌热处理风味酸奶/香蕉牛奶/草莓酸奶 均→酸奶/牛奶，纯猕猴桃/苹果/咖啡仍正确**；`xcodebuild` **BUILD SUCCEEDED**。
- 说明：该匹配只在「云端/文本模型估算且无真实营养成分表」时启用（本地标签 OCR 已优先用标签值，见上一条），故风味误匹配只在聊天/文本记账场景生效。

## 修复：营养成分表本地 OCR 被营养库覆盖
- 现象：用户拍酸奶营养成分表（能量 379kJ、蛋白质 3.1g、脂肪 3.3g、碳水 12.0g），识别结果页显示热量 61 kcal、蛋白质 1.1g、碳水 15.0g、脂肪 0.5g——这是猕猴桃的通用营养值。
- 根因：`ResultConfirmView.swift` 在 `onAppear` 时无条件用 `NutritionLibrary.shared.match(foodName)` 覆盖所有宏量/热量。虽然 OCR 已正确读出包装标签，但「猕猴桃果酱」命中了营养库的「猕猴桃」条目，导致标签值被覆盖。
- 修复：`AIA/AIA/ResultConfirmView.swift`。当识别来源 `source == .local`（即本地营养成分表 OCR）时，保留标签 OCR 值，仅展示提示「按包装标签识别」；只有云端/文本模型估算结果才允许营养库校正。
- 编译验证：`xcodebuild` **BUILD SUCCEEDED**。
- 待用户：重编译/重装 App，再拍同一瓶酸奶，应显示 90.6 kcal / 3.1g 蛋白 / 3.3g 脂肪 / 12.0g 碳水。

## 营养库匹配全面优化：别名归一表 + 调料前缀护栏
- 需求：用户「看看其他食物是否也有类似问题，也一并优化」（继头名词优先改进之后的普查）。
- 诊断：写 `/tmp/diag_nutrition.swift`（真实全表 + 新 match 逻辑）跑 ~40 复合食物/别名。发现头名词优先已正确处理绝大多数复合词（猕猴桃酸奶→酸奶、皮蛋瘦肉粥→粥、扬州炒饭→炒饭、牛肉拉面→拉面、可口可乐→可乐），残留三类：
  ① **别名错配/缺失**：`凤梨→梨`(错，含"梨"子串)、`奇异果/圣女果/提子/车厘子/卡布奇诺/方便面→nil`。
  ② **调料前缀误当主体**：`可乐鸡翅→可乐`(43kcal，实为炸鸡类)。
  ③ 头名词不在库→回退配料（`咖喱牛肉饭→牛肉`、`西红柿鸡蛋面→鸡蛋`），可接受。
- 修复（`AIA/AIA/NutritionLibrary.swift`）：
  - 新增 `aliases: [String:String]` 别名归一表（水果/主食/饮品/肉蛋异名，如 凤梨→菠萝、奇异果→猕猴桃、圣女果→番茄、提子→葡萄、车厘子→樱桃、方便面→面条、卡布奇诺→拿铁、里脊→瘦肉）。归一在**精确之后、子串之前**执行，故别名优先级高于子串——同时修掉「凤梨含梨」这类子串错配。
  - 新增 `seasoningPrefixes: Set<String>` 调料/做法前缀护栏（可乐/糖醋/红烧/麻辣/回锅…）。当**唯一命中键**是调料词、位于名称最前端、后面还有主体时，返回 nil（交云端估算），避免把"可乐"当鸡翅的营养主体。
  - 补一条基准 `樱桃`(46/1.1/10.2/0.2) 供车厘子别名指向。
- 铁律（写入 MEMORY.md）：NutritionLibrary 匹配顺序 = **精确 → 别名归一 → 子串(头名词/靠后优先) → 调料前缀护栏(命中调料前缀且在最前端则弃)**。新增食物异名走 aliases，不要往 rows 里塞异名；调料/做法词若与独立食物键重名（可乐），必须进 seasoningPrefixes。
- 验证：`/tmp/diag_nutrition.swift` 所有真错配已修复；`xcodebuild` 见下条。
